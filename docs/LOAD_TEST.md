# 부하 테스트 (7단계)

`cmd/loadtest`가 **실제 fleetd 프로세스**를 띄우고, 가짜 로봇은 Mosquitto를 거쳐 MQTT로, 가짜 브라우저는 `/ws/live` WebSocket으로 붙인다.
fleetd 코드는 그대로이고, 비교할 다른 설계만 숨은 스위치(`-bench-encode-per-client`, `-bench-block-slow`, `-h`에 안 보임)로 켠다.
결과는 2026-11-03에 아래 PC에서 실제로 돌린 값이다.

## 요약

| 비교 (로봇 500대, 모두 이동) | 결과 (중앙값, 3번씩) |
|---|---|
| 묶음을 **한 번 인코딩** vs **브라우저마다** (브라우저 20개) | 인코딩 묶음당 1번 vs 20번. 빠른 브라우저 지연 p50 1.0 → 3.1 ms, p99 1.6 → 5.7 ms. fleetd CPU 9% → 14% |
| 같은 비교, 브라우저 60개 | 인코딩 1번 vs 60번. CPU 13% → 26%, 지연 p50 1.0 → 7.7 ms, p99 4.7 → 17.6 ms |
| 느린 브라우저 2개: **버림** vs **기다림** | 빠른 브라우저 18개가 받는 묶음 6.7 → 2.0개/초, p99 지연 1.6 ms → 1,001 ms, Tick이 95% 시간을 기다림. 버림은 느린 브라우저에서 9.6개/초를 버리고 스냅샷으로 다시 맞춤. 단 느린 브라우저가 보는 상태는 버림에서도 중앙값 3.3초·최대 4.0초 묵음(기다림 7.0·7.9초) |
| 500대 동시 재접속: **jitter** vs **없음** (브로커 2.5초 거절) | 100 ms 동안 최대 시도 59 vs 500. 끊김이 끝난 뒤 실패한 시도 0 vs 105 [47–181](부하 테스트 프록시의 접속 대기열 거절). 모두 다시 붙기까지 8.3 vs 7.05초 |
| 같은 비교, 3.5초 거절 | 최대 시도 64 vs 500, 실패 0 vs 149 [14–188], 모두 다시 붙기까지 **9.4 vs 15.1초** |

## 부하가 몰리는 곳

- **로봇 → 서버:** 로봇 500대 × 위치 5 Hz = 초당 2,500개 + 상태 1 Hz = 500개. 메시지가 작고 seq 비교와 맵 갱신뿐이라 무겁지 않다.
- **서버 → 브라우저:** 묶음 크기는 바뀐 로봇 수에 비례하고, 전송량은 **로봇 수 × 브라우저 수 × 빈도**다. 로봇 500대가 모두 움직이면 묶음 하나가 약 80 KB,
  0.15초마다 → 브라우저 하나에 초당 약 530 KB, 20개면 초당 10 MB를 서버가 쓴다. 여기서 두 설계가 갈린다.
  - **한 번 인코딩 vs 브라우저마다 인코딩:** 같은 묶음을 브라우저마다 JSON으로 만들면 인코딩이 브라우저 수만큼 늘어난다(로봇 수 × 브라우저 수).
  - **느린 브라우저: 버리기 vs 기다리기:** 한 브라우저를 기다리면 모든 브라우저가 그 브라우저 속도로 떨어진다.
    fleetd는 그 브라우저의 오래된 묶음을 버리고 지금 상태 스냅샷 하나로 다시 맞춘다.
- **동시 재접속(폭풍):** 브로커 재시작이나 현장 네트워크가 잠깐 끊기면 로봇 전부가 한꺼번에 다시 붙는다. jitter가 없으면 모두 같은 순간에 시도하고,
  실패한 것들은 다음에도 같은 순간에 시도한다.

## 방법

| 항목 | 값 |
|---|---|
| 기계 | AMD Ryzen 5 7500F (6코어 12스레드), RAM 32 GB, Windows 11 Home, Go 1.27.3, Mosquitto 2.1.2(기본 설정, localhost). fleetd·Mosquitto·부하 생성기가 한 PC를 같이 쓴다 |
| 로봇 | 500대, 각자 MQTT 연결 하나(autopaho, fleetd와 같은 라이브러리). 모두 반지름 1.5 m 원을 0.8 m/s로 돈다(가장 나쁜 경우: 모든 묶음에 500대가 다 들어감) |
| 위치·상태 | 어댑터(`fleet_logic.py`)와 같은 규칙: 위치는 5 Hz로 확인해 5 cm·2° 넘게 움직였으면 보냄(아니면 1초마다), QoS 0. 상태는 1초마다 QoS 1 |
| 브라우저 | `/ws/live` 20개. 그중 2개는 묶음 하나를 읽을 때마다 0.5초 쉰다(느린 브라우저). 묶음은 앞부분(`type`, `time`)만 읽어 부하 생성기 CPU를 아낀다 |
| 지연 | 묶음 안의 서버 시각(`time`, 레지스트리를 읽은 순간) → 브라우저가 받은 순간. 같은 PC라 시계는 같지만 Windows 벽시계가 약 0.5 ms 단위로 움직여 그 아래는 잡음이다(측정마다 보고서에 찍음) |
| CPU | fleetd 프로세스의 CPU 시간 증가분 ÷ 측정 시간(한 코어 = 100%). Windows `GetProcessTimes`, Linux `/proc/<pid>/stat` |
| 버림·스냅샷 | `GET /live/stats`의 `dropped`, `resyncs`, `blocked_ms` 증가분. 느린 브라우저는 받은 스냅샷 수와, 읽은 묶음이 담은 상태의 나이(서버 시각 → 읽은 순간)도 잰다 |
| 측정 | 로봇이 모두 ONLINE이고 브라우저가 모두 붙은 뒤 5초 예열, 15초 측정 |
| 재접속 폭풍 | 로봇과 브로커 사이에 TCP 프록시를 두고(fleetd는 브로커에 직접 붙음) 모든 연결을 한 번에 끊은 뒤 정해진 시간 동안 접속을 받자마자 끊는다(브로커가 내려간 것처럼 빨리 실패). 로봇 쪽에서 연결 시도 시각, 성공 시각, 실패 원인을 기록하고, fleetd `/robots`를 0.1초마다 읽어 모두 ONLINE이 되는 시각을 잰다 |
| 백오프 | jitter 있음 = `mqttx.Backoff`(fleetd가 쓰는 것: 1·2·4… 초, 최대 30초, ±50%). 없음 = 같은 간격에서 jitter만 뺌. autopaho는 첫 시도 앞에서도 백오프를 기다린다(끊긴 뒤 첫 시도가 0.5~1.5초 / 정확히 1초 뒤) |
| 반복 | 시나리오마다 3번, 매번 새 fleetd(새 DB, `-elevators none`, `-log warn`, `-mqtt-id fleetd-loadtest`). 시나리오를 번갈아 돈다(A B C A B C …: PC 상태가 시간에 따라 바뀌어도 한 시나리오에 몰리지 않게). 표는 중앙값 [최소–최대]. 재접속 폭풍 표는 번갈아 돌리기 전에 잰 것이다 |

명령(Mosquitto가 떠 있어야 한다. `loadtest` 네 줄이 각각 약 5분·2분·2분·1분 반):

```bat
go build -o bin\fleetd.exe .\cmd\fleetd
go run .\cmd\loadtest -fleetd bin\fleetd.exe -machine "AMD Ryzen 5 7500F (6 cores / 12 threads), 32 GB RAM, Windows 11 Home, Mosquitto 2.1.2" -md out.md -json out.json
go run .\cmd\loadtest -fleetd bin\fleetd.exe -scenarios storm-jitter,storm-nojitter -outage 3500ms -md out2.md
go run .\cmd\loadtest -fleetd bin\fleetd.exe -scenarios block -slow 1 -md out4.md
go run .\cmd\loadtest -fleetd bin\fleetd.exe -scenarios default,per-client -clients 60 -slow 0 -md out3.md
```

옵션: `-robots`, `-clients`, `-slow`, `-slow-delay`, `-moving`(움직이는 비율), `-warmup`, `-window`, `-repeat`, `-outage`, `-scenarios`,
`-attach URL -pid N`(이미 떠 있는 fleetd를 잼, 스위치는 못 바꿈), `-keep-logs`, `-slow-rcvbuf N`(느린 브라우저의 소켓 받는 버퍼), `-check`(아래 CI 조건을 못 맞추면 실패).
CI는 `-robots 300 -clients 4 -slow 1 -slow-delay 1s -slow-rcvbuf 32768 -warmup 10s -window 10s -repeat 1 -check`로 기능만 확인한다(이 PC에서도 통과, 약 1분 반).

### 해석: 묶음

- **기본(한 번 인코딩 + 버림)은 로봇 500대 + 브라우저 20개에서 fleetd CPU가 한 코어의 약 9%다.** 가짜 로봇이 위치를 초당 2,500개 보내고, fleetd는 80 KB 묶음을 초당 6.7개 만들어 20곳에 보낸다.
  빠른 브라우저 지연은 중앙값 1.0 ms, p99 1.6 ms다(0.5 ms 벽시계 단위 수준).
- **브라우저마다 인코딩하면 인코딩 수가 브라우저 수만큼 늘고, 먼저 지연에서 드러난다.** 20개에서 지연 중앙값 1.0 → 3.1 ms, p99 1.6 → 5.7 ms. 마지막 브라우저는 앞의 인코딩을 다 기다린다.
  CPU는 9% → 14%(범위 8~9 / 12~17, 번갈아 잰 이번에는 겹치지 않음). 60개에서는 CPU 13% → 26%, 지연 중앙값 1.0 → 7.7 ms, p99 4.7 → 17.6 ms로 브라우저 수에 비례해 커진다.
  한 번 인코딩이면 브라우저를 20 → 60개로 늘려도 지연 중앙값은 1.0 ms 그대로다.
- **느린 브라우저를 기다리면 모든 브라우저가 느린 브라우저 속도가 된다.** 빠른 브라우저가 받는 묶음이 초당 6.7 → 2.0개, p99 지연이 1.6 ms → 1,001 ms, Tick은 측정 시간의 95%를 기다렸다.
  p99가 왜 1초(느린 브라우저의 읽기 간격 0.5초의 두 배)인지는 확인하지 못했다. 처음에는 "느린 브라우저 2개 × 0.5초"라고 적었는데, 느린 브라우저를 1개로 해도 p99가 1.0초여서 그 설명은 틀렸다.
  (CI 크기로 느린 브라우저가 1초마다 읽게 한 실행에서는 p99가 3.0초였다. 느린 쪽 전송 고루틴·대기열·소켓 버퍼가 함께 밀리는 것으로 보이지만 추측이다.)
  기다리기 모드에서는 느린 브라우저도 이득이 없다: 보는 상태가 중앙값 7.0초, 최대 7.9초 묵었다(대기열과 소켓 버퍼가 옛 묶음으로 가득 찬 채 그대로 읽음).
  첫 실행에서 지연 중앙값이 2~424 ms로 갈린 것은 Go 맵 순회 순서에 따라 빠른 브라우저가 느린 브라우저보다 먼저 받기도 나중에 받기도 하기 때문으로 보인다(이번 3번은 1.1~1.5 ms).
- **버림은 빠른 브라우저를 지키지만, 느린 브라우저가 보는 상태는 몇 초 묵는다.** 기본 동작은 느린 브라우저 2개에서 초당 9.6개를 버리고 스냅샷으로 다시 맞추며(15초에 18번), 빠른 브라우저는 영향이 없다.
  그러나 느린 브라우저가 보는 상태는 중앙값 3.3초, 최대 4.0초 묵었다. 버린 뒤 넣는 스냅샷 자체는 최신이지만, 그 앞에 이미 보낸 묶음(전송 고루틴이 쓰는 중인 것 + 소켓 버퍼)이 있고,
  스냅샷 뒤로 다시 대기열(8칸)이 차서 느린 브라우저는 그것들을 0.5초에 하나씩 순서대로 읽는다. 8칸 × 0.5초 = 4초가 최대 나이와 맞는다.
  즉 지금 구조가 보장하는 것은 "빈틈 없이 다시 맞춘다"와 "다른 브라우저를 막지 않는다"이지, "느린 브라우저가 최신을 본다"가 아니다.
  나이를 묶으려면 느린 브라우저용 대기열을 아주 작게(1~2칸) 하거나, 브라우저마다 "최신 하나만" 두는 방식(새 묶음이 오면 대기 중인 것을 버리고 스냅샷/합친 delta로 바꿈)이 필요하고,
  소켓 버퍼에 쌓인 몫까지 줄이려면 서버 쪽 쓰기 버퍼를 줄이거나 브라우저가 다음 묶음을 요청하는 흐름 제어가 필요하다. 이번 단계에서는 바꾸지 않았다(README 알려진 한계).
- 부하 생성기(로봇 500대 + 브라우저)가 fleetd보다 CPU를 더 쓴다(16~31%). fleetd와 합쳐도 12스레드 중 한 스레드 남짓이라 CPU가 모자라지는 않았지만(Mosquitto CPU는 재지 않음), 같은 PC라는 점은 아래 한계에 적었다.

### 해석: 재접속 폭풍

- **jitter의 효과는 순간 부하다.** jitter가 없으면 500대가 같은 100 ms 안에 연결을 시도한다(매번 500). jitter가 있으면 100 ms당 최대 약 60이고 시도가 8초 넘게 퍼진다.
- **그 순간 부하는 연결을 실패시켰다. 다만 거절한 쪽은 이 시험 장치다.** jitter가 없으면 끊김이 끝난 뒤의 시도 중 실행마다 14~188개(2.5초 끊김 중앙값 105, 3.5초 끊김 149)가 "actively refused"로 실패했다.
  거절한 것은 로봇이 처음 닿는 **부하 테스트 자신의 Go TCP 프록시 listen 소켓**(Windows의 접속 대기열)이다. 프록시 → Mosquitto 연결 실패는 0이었으므로 Mosquitto는 거절하지 않았다.
  로봇이 Mosquitto에 직접 붙었다면 Mosquitto의 listen 대기열이 같은 자리에 서겠지만, 거기서 몇 개가 거절될지는 **재지 않은 추측**이다(대기열 크기와 OS에 달렸다).
  jitter가 있으면 끊김이 끝난 뒤의 실패는 0이었다.
- **"모두 다시 붙기까지"는 jitter가 늘 빠른 것이 아니다.** 2.5초 거절에서는 jitter 없는 쪽이 더 빨랐다(7.05 vs 8.28초). 3초에 500대가 한꺼번에 와서 대부분 붙고 거절된 일부만 7초에 붙었기 때문이다.
  3.5초 거절에서는 반대로 jitter 없는 쪽이 3초 시도를 통째로 놓치고 7초에 500대가 다시 몰려 일부가 또 거절되어 15초에야 다 붙었다(jitter 9.4초).
  jitter 없는 쪽은 끊김 길이가 시도 시각과 어떻게 맞물리는지에 따라 7초도 15초도 되고, jitter 쪽은 잰 두 경우(2.5초, 3.5초 끊김) 모두 끊김이 끝난 뒤 5.7~6.0초였다.
  백오프가 두 배씩 늘어나므로 더 긴 끊김에서도 그렇다고 할 수는 없다(재지 않음).
  jitter는 평균 복구 시간을 줄이는 장치가 아니라 **동시에 몰리는 것을 막는** 장치다.
- fleetd 쪽은 어느 경우든 가벼웠다(CPU 한 코어의 4~10%). 브로커에서 다시 오는 메시지를 받아 STALE → ONLINE(연속 3번)으로 되돌리는 것뿐이고, fleetd 자신의 MQTT 연결은 끊기지 않았다.
  jitter 없는 쪽은 모두 같은 순간에 돌아와 마지막 연결 뒤 약 0.6초 만에 모두 ONLINE이 됐다.

## 한계

- fleetd, Mosquitto, 부하 생성기가 한 PC에 있다. 네트워크 지연·대역폭은 없고(loopback), 부하 생성기 CPU(20~30%)가 같은 PC를 쓴다. 다른 PC에서는 숫자가 다르다. 비교(같은 조건의 A vs B)로 읽어야 한다.
- 로봇 500대가 모두 계속 움직이는 최악 조건이다. 실제로는 서 있는 로봇이 많아 묶음이 훨씬 작다(`-moving 0.2` 등으로 바꿀 수 있다).
- 지연은 0.5 ms 단위 벽시계로 쟀다. 1 ms 근처 값은 "1 ms 안팎"으로만 읽는다.
- 재접속 폭풍은 로봇 연결을 프록시에서 끊어 흉내 냈다. 실제 브로커 재시작(세션·retained 복구, 브로커 자신의 시작 시간)은 넣지 않았다. 연결 시도는 로봇 쪽에서 셌다.
- 묶음 비교에서 느린 브라우저는 "0.5초마다 하나씩 읽음, OS 기본 소켓 버퍼" 한 종류다(CI는 `-slow-rcvbuf 32768`로 받는 버퍼를 줄인다). 아예 읽지 않는 브라우저는 5초 쓰기 제한으로 닫히는 것을 `internal/api` 테스트(`TestLiveSlowClientClosed`)가 확인한다.
- 숫자를 보는 자동 검사는 없다. CI의 `loadtest-smoke`는 작은 규모로 기능만 확인한다(공유 러너는 숫자가 흔들린다).
